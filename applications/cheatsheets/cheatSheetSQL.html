2. Grundkonzepte 2. Core Concepts

2.1 Relationale Datenbanken (RDBMS) 2.1 Relational Databases (RDBMS)

Ein Relationales Datenbankmanagementsystem speichert Daten in Form von Tabellen (Relationen). Jede Tabelle besteht aus Spalten (Attribute) und Zeilen (Datensätze). Tabellen können über gemeinsame Felder miteinander verknüpft (relatiert) werden. Der Begriff "relational" geht auf E. F. Codd (1970) zurück. A Relational Database Management System stores data in the form of tables (relations). Each table consists of columns (attributes) and rows (records). Tables can be linked (related) to each other using shared fields. The term "relational" goes back to E. F. Codd (1970).

2.2 Primär- & Fremdschlüssel 2.2 Primary & Foreign Keys

Primärschlüssel (Primary Key)Primary Key (PK)

Ein eindeutiger Identifikator für jeden Datensatz in einer Tabelle. Darf niemals NULL sein und muss einzigartig (UNIQUE) sein. Ein Primärschlüssel kann aus einer oder mehreren Spalten bestehen (zusammengesetzter Schlüssel). (z.B. user_id). A unique identifier for each record in a table. It must never be NULL and must be completely unique. A primary key can consist of one or more columns (composite key). (e.g., user_id).

Fremdschlüssel (Foreign Key)Foreign Key (FK)

Ein Feld in einer Tabelle, das auf den Primärschlüssel einer anderen Tabelle verweist, um eine Beziehung herzustellen (Referentielle Integrität). Der Fremdschlüssel kann NULL sein, wenn die Beziehung optional ist. (z.B. customer_id in der Tabelle orders). A field in a table that references the Primary Key of another table to establish a relationship (Referential Integrity). The foreign key can be NULL if the relationship is optional. (e.g., customer_id in the orders table).

2.3 Das 3-Schichten-Modell (ANSI/SPARC) 2.3 The Three-Schema Architecture (ANSI/SPARC)

Das 3-Schichten-Modell – 1975 vom ANSI/SPARC-Komitee standardisiert – beschreibt, wie ein DBMS Daten auf drei unterschiedlichen Abstraktionsebenen darstellt. Es ist die theoretische Grundlage der wichtigsten Eigenschaft moderner Datenbanken: der Trennung von logischer Sicht und physischer Speicherung. The three-schema architecture – standardized in 1975 by the ANSI/SPARC committee – describes how a DBMS represents data on three different levels of abstraction. It is the theoretical foundation of the most important property of modern databases: the separation of logical view and physical storage.

Warum das Ganze? Datenunabhängigkeit Why Bother? Data Independence

Durch die Zwischenschicht der konzeptionellen Ebene können Änderungen auf einer Ebene erfolgen, ohne die anderen zu berühren. Das nennt man Datenunabhängigkeit. Thanks to the intermediate conceptual level, changes can be made at one level without affecting the others. This property is called data independence.

Logische Datenunabhängigkeit Logical Data Independence

Änderungen am konzeptionellen Schema (z. B. eine neue Spalte) dürfen die externen Sichten nicht kaputt machen. Changes to the conceptual schema (e.g. a new column) must not break the external views.

Physische Datenunabhängigkeit Physical Data Independence

Änderungen am internen Schema (z. B. neuer Index) dürfen das konzeptionelle Schema und damit die Anwendungen nicht ändern. Changes to the internal schema (e.g. a new index) must not modify the conceptual schema, and thus not the applications.

Beispiel: Ein Index wird hinzugefügt Example: An Index Is Added

Der DBA legt einen Index auf users.email an (interne Ebene). Die Anwendung muss nichts ändern – die SELECT-Abfragen liefern weiterhin dieselben Ergebnisse, nur schneller. Das ist gelebte physische Datenunabhängigkeit. The DBA creates an index on users.email (internal level). No application needs to change – SELECT queries return the same results, just faster. This is physical data independence in action.

4. DML (Data Manipulation Language) 4. DML (Data Manipulation Language)

DML-Befehle verwalten die eigentlichen Daten innerhalb der Tabellen (CRUD-Operationen außer Read). DML commands manage the actual data within the tables (CRUD operations excluding Read).

INSERT

Fügt neue Zeilen in eine Tabelle ein. Inserts new rows into a table. 

INSERT INTO users (username, email)
VALUES ('Alice', 'alice@mail.com');

INSERT INTO users (username, email)
VALUES
    ('Bob', 'bob@mail.com'),
    ('Carol', 'carol@mail.com');

UPDATE

Ändert bestehende Daten. Ohne WHERE werden alle Zeilen geändert! Modifies existing data. Without WHERE, all rows are changed! 

UPDATE users
SET email = 'new@mail.com'
WHERE id = 1;

DELETE

Vergiss niemals die WHERE-Klausel, sonst löschst du die gesamte Tabelle! Never forget the WHERE clause, or you will delete the entire table! 

DELETE FROM users WHERE id = 1;

DELETE FROM users WHERE created_at < '2020-01-01';

5. DQL (Data Query Language) 5. DQL (Data Query Language)

DQL besteht hauptsächlich aus dem SELECT-Befehl. Er wird verwendet, um Daten abzufragen und zu filtern. DQL primarily consists of the SELECT command. It is used to query and filter data.

5.1 Anatomie einer Abfrage 5.1 Anatomy of a Query 

SELECT column1, COUNT(column2)  -- 1. Was wollen wir sehen? (Projektion)
FROM table_name               -- 2. Woher kommen die Daten? (Relation)
WHERE condition               -- 3. Filter für Zeilen
GROUP BY column1              -- 4. Gruppierung für Aggregationen
HAVING COUNT(column2) > 5     -- 5. Filter für gruppierte Daten
ORDER BY column1 DESC         -- 6. Sortierung (ASC/DESC)
LIMIT 10;                     -- 7. Begrenzung der Ausgabe

  • Erfüllt 1NFMeets 1NF
  • Keine partiellen Abhängigkeiten: Jedes Nicht-Schlüssel-Attribut muss vom gesamten Primärschlüssel abhängen (relevant bei zusammengesetzten Schlüsseln).No partial dependencies: Every non-key attribute must depend on the entire primary key (relevant for composite keys).

BeispielExample

Tabelle Bestellung(PK: OrderID, ProductID, Menge, ProductName) – ProductName hängt nur von ProductID ab, nicht vom gesamten Schlüssel. → Aufteilen in Bestellung und Product. Table Order(PK: OrderID, ProductID, Quantity, ProductName) – ProductName depends only on ProductID, not the full key. → Split into Order and Product.

7.3 Dritte Normalform (3NF) 7.3 Third Normal Form (3NF)

RegelnRules

  • Erfüllt 2NFMeets 2NF
  • Keine transitiven Abhängigkeiten: Kein Nicht-Schlüssel-Attribut darf von einem anderen Nicht-Schlüssel-Attribut abhängen.No transitive dependencies: No non-key attribute may depend on another non-key attribute.

BeispielExample

Tabelle Mitarbeiter(MitarbeiterID, Name, AbteilungID, Abteilungsname) – Abteilungsname hängt von AbteilungID ab (nicht direkt vom Schlüssel). → Aufteilen in Mitarbeiter und Abteilung. Table Employee(EmployeeID, Name, DepartmentID, DepartmentName) – DepartmentName depends on DepartmentID (not directly on the key). → Split into Employee and Department.

7.4 Denormalisierung 7.4 Denormalization

Denormalisierung ist die bewusste Rücknahme der Normalisierung, um Leseperformance zu verbessern. Redundanz wird in Kauf genommen, um teure Joins zu vermeiden. Typisch für Data Warehouses und Reporting-Systeme. Denormalization is the deliberate reversal of normalization to improve read performance. Redundancy is accepted to avoid expensive joins. Typical for data warehouses and reporting systems.

8. Transaktionen & ACID 8. Transactions & ACID

Eine Transaktion ist eine logische Arbeitseinheit, die aus mehreren SQL-Befehlen bestehen kann und entweder vollständig oder gar nicht ausgeführt wird ("Alles-oder-Nichts-Prinzip"). A transaction is a logical unit of work that can consist of multiple SQL statements and is executed either completely or not at all ("all-or-nothing principle").

8.1 ACID-Eigenschaften 8.1 ACID Properties

A – Atomicity

Atomarität: Entweder alle Operationen der Transaktion werden ausgeführt oder keine. Atomicity: Either all operations of the transaction are executed or none.

C – Consistency

Konsistenz: Die Datenbank bleibt in einem gültigen Zustand (alle Constraints erfüllt). Consistency: The database remains in a valid state (all constraints satisfied).

I – Isolation

Isolation: Parallele Transaktionen beeinflussen sich nicht gegenseitig. Isolation: Concurrent transactions do not affect each other.

D – Durability

Dauerhaftigkeit: Nach einem COMMIT sind die Änderungen permanent gespeichert, auch bei Systemabsturz. Durability: After a COMMIT, changes are permanently stored, even on system crash.

8.2 TCL – Transaction Control Language 8.2 TCL – Transaction Control Language 

BEGIN TRANSACTION;    -- Transaktion starten

UPDATE konto SET saldo = saldo - 100 WHERE id = 1;
UPDATE konto SET saldo = saldo + 100 WHERE id = 2;

COMMIT;                 -- Änderungen permanent speichern
-- oder bei Fehler:
ROLLBACK;               -- Alle Änderungen verwerfen
Deadlock:Deadlock: Zwei Transaktionen warten aufeinander und blockieren sich gegenseitig. Das DBMS erkennt Deadlocks und rollt eine Transaktion automatisch zurück. Two transactions wait for each other and block each other. The DBMS detects deadlocks and automatically rolls back one transaction.

9. Index & Performance 9. Index & Performance

9.1 Indizes 9.1 Indexes

Ein Index ist eine Datenstruktur (meist ein B-Baum), die den Zugriff auf Zeilen beschleunigt – ähnlich wie das Stichwortverzeichnis eines Buchs. Er beschleunigt WHERE, JOIN und ORDER BY, verlangsamt aber INSERT, UPDATE und DELETE (weil der Index mitgepflegt werden muss). An index is a data structure (usually a B-tree) that speeds up access to rows – similar to a book's index. It speeds up WHERE, JOIN, and ORDER BY but slows down INSERT, UPDATE, and DELETE (because the index must be maintained).

10. Views, Stored Procedures & Trigger 10. Views, Stored Procedures & Triggers

10.1 Views (Sichten) 10.1 Views

Eine View ist eine gespeicherte Abfrage, die wie eine virtuelle Tabelle fungiert. Sie speichert keine eigenen Daten, sondern berechnet das Ergebnis bei jedem Zugriff neu. A view is a stored query that acts as a virtual table. It does not store its own data but recalculates the result on each access. 

CREATE VIEW v_active_users AS
SELECT id, username, email
FROM users
WHERE active = TRUE;

SELECT * FROM v_active_users;
Vorteile:Benefits:
  • Sicherheit: Nutzer sieht nur bestimmte SpaltenSecurity: user sees only certain columns
  • Vereinfachung: komplexe Joins als eine TabelleSimplification: complex joins as one table
  • Logische DatenunabhängigkeitLogical data independence

10.2 Stored Procedures 10.2 Stored Procedures

Eine Stored Procedure ist ein vorkompiliertes SQL-Programm, das in der Datenbank gespeichert ist und Parameter akzeptieren kann. Sie verbessert Performance und Wiederverwendbarkeit. A stored procedure is a precompiled SQL program stored in the database that can accept parameters. It improves performance and reusability. 

CREATE PROCEDURE GetUsersByCity(IN city_name VARCHAR(50))
BEGIN
    SELECT * FROM users WHERE city = city_name;
END;

CALL GetUsersByCity('Berlin');

10.3 Trigger 10.3 Triggers

Ein Trigger ist ein automatisch ausgeführtes Programm, das bei bestimmten Ereignissen (INSERT, UPDATE, DELETE) auf einer Tabelle "feuert". Er dient zur Protokollierung, Validierung oder Durchsetzung von Geschäftsregeln. A trigger is an automatically executed program that "fires" on certain events (INSERT, UPDATE, DELETE) on a table. It is used for logging, validation, or enforcing business rules. 

CREATE TRIGGER log_user_insert
AFTER INSERT ON users
FOR EACH ROW
BEGIN
    INSERT INTO audit_log (table_name, action, user_id)
    VALUES ('users', 'INSERT', NEW.id);
END;

SQL injection is one of the most common security vulnerabilities. An attacker injects SQL code via user input (e.g., login form) to manipulate the database or read data.

-- Sicher: Prepared Statement
